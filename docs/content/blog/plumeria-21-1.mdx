Plumeria v21.1 makes `sort-properties` read keys from `createStatic`, so it agrees with `no-order-dependent-overlap` on where a breakpoint goes.

## 1. `createStatic` keys in `sort-properties`

`sort-properties` did not read a computed key such as `[media.desktop]`. It treated the key as one without a name and placed it after the properties but before the pseudo-classes and the `@media` keys. `no-order-dependent-overlap` reads the same key as the query it holds, so the two rules could ask for opposite orders:

```ts
// tokens.ts
export const media = css.createStatic({
  desktop: '@media (min-width: 992px)',
});
```

```ts
const styles = css.create({
  grid: {
    display: 'grid',
    '@media (min-width: 640px)': { gap: 8 },
    [media.desktop]: { gap: 16 },
  },
});
```

Written this way, `sort-properties` asked for `[media.desktop]` before the 640px query and reported it as `Property ""`. Written the other way, `no-order-dependent-overlap` reported the 992px query for coming before the broader one. Neither order passed, and the lint that runs in the build stopped either way.

`sort-properties` now resolves the key, including one imported from another module, and sorts `[media.desktop]` as `@media (min-width: 992px)`. It goes with the other at-rules after the pseudo-classes, in the order it is written, so the example above passes both rules.

## Upgrading

A `createStatic` key written before a pseudo-class, such as `[media.desktop]` before `':hover'`, is now reported. The lint that runs in the build stops on warnings, so run the fix once after upgrading:

```bash
pnpm up "@plumeria/*" --latest
npx -p @plumeria/eslint-plugin plumeria-lint --fix
```

The fix only moves keys inside a style object, and the generated CSS stays the same.

## Release notes

## 21.1.2 (Oct 23, 2026)

- Fix: a received style can be composed onto a component the build never scans, such as a `@plumeria/headlessui` part, with `classStyle={[styles.base, classStyle]}` instead of failing the build
- Fix: passing a received style to a component that declares the style prop fails the build at that attribute, even when the same style is also applied to an element, instead of the style being silently dropped
- Fix: `no-style-prop-relay` reports a received style passed to a component that declares the style prop, the same case the build stops at, including a component imported from another file
- Fix: `no-order-dependent-overlap` no longer reports selectors that cannot match at the same time: the same attribute with different values, `:not([attr])` with `[attr=...]`, `:user-valid` with `:user-invalid`, `:playing` with `:paused`, `:dir(ltr)` with `:dir(rtl)`, and odd with even `:nth-*()`
- Fix: `no-style-prop-relay` reports a file the editor opens under a path that differs from the real one, such as a different letter case on macOS
- Update: Next.js in `@plumeria/next-plugin` devDependencies to 16.4.2

## 21.1.1 (Oct 22, 2026)

- Fix: the transform scans the project from the bundler root (Jest `rootDir` in swc-jest) instead of the process working directory, so a build started from a monorepo root no longer rescans every workspace on each file

## 21.1.0 (Oct 20, 2026)

- Update: `sort-properties` reads a computed key from `css.createStatic`, such as `[media.desktop]`, as the at-rule it holds and sorts it with the other at-rules, after the pseudo-classes, so it no longer conflicts with `no-order-dependent-overlap`; `plumeria-lint --fix` moves the keys already written
